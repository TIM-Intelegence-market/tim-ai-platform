# Mission 09 task governance (#68)

Guard that makes mission-task creation idempotent, update-first and duplicate-safe.
Code: `src/task_governance/`. Tests: `tests/task_governance/`.

## Identity

`canonical_task_key = MISSION|PHASE|TASK_TYPE|TARGET|schema_version`, for example
`M09|P0|BASELINE_ARCHITECTURE_AUDIT|TIM|v1`. The fingerprint is `sha256(key)`.
Titles and bodies are display text and never part of the identity. Empty parts or
parts containing `|` are rejected, not normalised.

## Flow (`ensure_task`)

1. Mapping for the fingerprint is MAPPED: update the issue (or apply the reopen policy). Nothing is created.
2. Mapping is BLOCKED: stay blocked, nothing is created.
3. Otherwise claim creation. The claim is a row in SQLite (`PRIMARY KEY fingerprint`, `UNIQUE canonical_key`), so threads and processes cannot both win it. Every claim carries a fencing token. A worker that loses returns `PENDING`. A claim is taken over only after its lease expired, never because the claimant name matches.
4. Uniqueness check before creating: search GitHub for the fingerprint marker (`<!-- TIM_TASK_FINGERPRINT:<sha> -->`).
   - `authoritative_hint` given and that issue exists: adopt it even if it predates the marker (#11 and #22–#65 do); `legacy_issues` (which require a hint) and other marker matches are recorded as duplicates
   - `authoritative_hint` given but the issue does not exist (`HINT_NOT_FOUND`), is a pull request, or has an untrusted author (`HINT_INVALID`): `BLOCKED`, nothing written into that issue, never a fallthrough to create
   - no hint, or the listed hint, and the task is listed in `legacy.py` for this repository (today: M09-P0 audit → #11, duplicates #22–#65 in `uezeyiraydin-cell/tim-ai-platform`): the listed authority and duplicates are used automatically. The table is bound to a repository, so other repositories are never touched
   - one marker match: adopt it (`RECOVERED`), no create
   - several matches without hint: `BLOCKED` plus a governance incident; a later call with a hint unblocks it only if the hint addresses the block: it must be one of the structured `block_candidates` stored on the task row (`AMBIGUOUS_DUPLICATES`, `DUPLICATE_AFTER_CREATE`) or differ from the rejected hint (`HINT_NOT_FOUND`, `HINT_INVALID`). An always-passed hint therefore cannot wave away unrelated incidents
   - none: ask the create authority (see "Create authority" below; a registry that the repository did not designate returns `BLOCKED` / `CREATE_NOT_AUTHORIZED`, releases its claim and records no create intent), then renew the lease (fails if the claim was taken over, then nothing is created) and create exactly once
5. Right before the create, the claim row records the create intent (`create_intent`, with the repository) in the same fenced update that renews the lease. A worker that later wins the claim of a row with this record never creates: if the marker lookup finds nothing it blocks as `CREATE_UNCERTAIN` (re-validated on every run, adopted as soon as the issue is visible); the record is cleared only when the gateway proved the request never left (`CreateNotSent`), by a later run of the same registry that finds the run which recorded it noted as ended without a request (`claim_ends`, see "Create claim and handover") or by an operator (`registry.confirm_not_created(fp, note)` after checking GitHub, refused until an hour after the recorded create started, checked in the same statement that clears it so a stale confirmation cannot clear a newer intent, and only correct when the operator also knows the worker that recorded it has stopped: a process paused right before its request can still send later, which no check on GitHub can rule out; the create claim label such a worker holds (see "Create claim and handover") keeps every other creator waiting until that worker finishes or an operator who knows it stopped deletes the label). This closes the gap of a creator that crashed or outlived its lease before it could record its issue while the listing still hid it. A task whose create was attempted in another repository returns `REPOSITORY_MISMATCH` (blocked rows and taken-over claims alike) and is not touched; a `POST_CREATE_CHECK_FAILED` row without a recorded repository (older release) returns `REPOSITORY_UNKNOWN` until an operator unblocks it with `hint=`. Every automatic release of a block (re-validation, re-check, a hint) and every negative re-check verdict only changes exactly the block it read, so a newer verdict of another worker stands. Registry files before schema 5 (`PRAGMA user_version`) get `create_intent` set on every row that is not `MAPPED`, once, with the quiet period starting at the migration (older releases did not record every create). If `create_issue` raises (for example a timeout after GitHub created the issue), record `CREATE_UNCERTAIN` and search by marker before anything else: one match is adopted, several block, none or unreachable keeps the claim held until the lease expires and re-raises. Otherwise: uniqueness check after creating. A second match blocks the task and records an incident. Nothing is ever closed automatically.
6. Adopt path order: mark duplicates and write the marker first (all idempotent, comment/label only), persist the mapping last, so a crash midway repeats the remaining steps on the next run.
7. Persist the mapping with the fencing token (issue number, repository, duplicate list). If the claim was lost meanwhile, the result is `BLOCKED` (`CLAIM_LOST_AFTER_CREATE`), never reported as cleanly created. The stale worker only records an incident and adds its issue to the winner's duplicate list; it cannot overwrite the winner's state (fenced writes).

A mapping is only synced for the repository it was created in; a call for another repository through the same registry returns `BLOCKED` (`REPOSITORY_MISMATCH`) and touches nothing.

A `MAPPED` task is never downgraded to `BLOCKED`, not even by an unfenced operator call; such a call only records an incident.

A failure before anything was created (for example GitHub unreachable) releases the claim.

## Policies

| Situation | Behaviour |
|---|---|
| Retry, restart, usage-limit resume | Same issue, updated |
| Closed authoritative issue | Never replaced. Reopened only with `ReopenPolicy.EXPLICIT` and `retry=True`, otherwise an audit comment |
| Historical duplicates | Kept as audit evidence, marked "duplicate of" once if not yet documented, never closed or deleted |
| Creator crashed after creating the issue | Nobody takes over before `lease_seconds` expired (a claimant name is not an identity); then the marker search finds the issue and adopts it, and if the listing still hides it the task blocks as `CREATE_UNCERTAIN` instead of creating (step 5) |
| Local registry lost | Mapping recovered from the GitHub marker |

The gateway interface has no close operation on purpose. `trusted_authors` is a required argument: pass the accounts allowed to own task issues, so someone who copies the marker into another issue cannot hijack or block a task (`None` trusts everyone and is a conscious choice). The hint is an operator decision, but it must be a confirmed issue (not a PR) by a trusted author.

## Limits

- Within one registry file the create-once guarantee is enforced by the database. Across registry files it is enforced by the create authority (below): only the registry that the repository designates may create, every other registry only reads, updates and adopts. Without a configured authority no registry creates at all.
- Fencing tokens are monotonic per task: rows are never deleted, releasing or unblocking sets `RELEASED`, so a stale worker's old token can never match a later claim.
- The gateway must declare `max_create_seconds` and enforce it as the `timeout` of `create_issue`; a create that exceeds it is recorded as a `SLOW_CREATE` incident. `lease_seconds` must be at least 4 times that value (`ValueError` otherwise). A create that still outlives its lease is recorded as `CLAIM_LOST_AFTER_CREATE` (the issue in the winner's duplicate list); within one registry file the create intent (step 5) keeps the winner from creating a second issue, and across registry files the create claim (see "Create claim and handover") does: GitHub offers no idempotency key for issues, but it creates a label at most once per name, and every create happens under such a label.
- Issues that predate the marker are only found through `authoritative_hint` or the built-in `legacy.py` table. A legacy task that is not listed there and is called without a hint creates a new issue. New legacy cases must be added to the table.

## Wiring a real GitHub gateway

Only results with `is_pull_request=False` count as task issues and pull requests are dropped. A marker match whose kind the gateway did not report blocks the task (`UNKNOWN_ISSUE_KIND`, same for a hint: `HINT_UNKNOWN_KIND`); it is neither adopted nor bypassed by creating. `UNKNOWN_ISSUE_KIND` is re-validated on every run and lifts itself once the gateway reports the field. `HINT_UNKNOWN_KIND` is re-validated with the pinned hint (see below), never without one, otherwise a run would create a duplicate of the legacy issue. A `MAPPED` row without a repository (none are written today) fails closed as `REPOSITORY_MISMATCH` and needs a manual repair. Author and repository comparisons ignore case and whitespace, and repository names also accept URL and `.git` forms. A gateway raises `CreateNotSent` only when `create_issue` failed before any request left the process; the guard still searches by marker and releases the claim only if nothing is visible. Any other exception is treated as uncertain (see step 5). A registry file from an earlier release is migrated on open (`PRAGMA user_version`, missing columns added).

Implement `IssueGateway` (`find_issues`, `create_issue`, `update_issue`, `reopen_issue`, `is_documented_duplicate`, `mark_duplicate`). `create_issue` and `update_issue` must embed `fingerprint_marker(fp)` in the body (the update back-fills issues that predate it). `mark_duplicate` and `update_issue` may only comment or label. `find_issues` should list issues and match the marker; GitHub's search index lags, and a lagging search would hide a just-created issue from the post-create check.

## Integration with #12 (Task Engine bridge)

The Task Engine (`src/task_engine`, PR #119) is a local task store and creates no GitHub issues. `sync_engine_task_to_issue(engine, task_id, registry, gateway, mission_id=, phase_id=, claimant=, trusted_authors=)` in `engine_bridge.py` connects it: it builds the `TaskRequest` from the engine task, binds the task to that identity in the registry, calls `ensure_task` and returns its result. **By default the engine is only read**: no state change, no checkpoint, no revision bump, whatever the outcome (`BLOCKED`, `PENDING`, an exception from GitHub, a task in any state). The task-to-issue mapping lives in the registry; `issue_for_engine_task(registry, task_id)` returns it. `record_checkpoint=True` is an opt-in that also writes the engine checkpoint `github_issue:<fingerprint[:16]>` (metadata: `issue`, `outcome`) for a task that is still `NEW`, `PLANNED`, `READY`, `IN_PROGRESS` or `VERIFYING` when the call ends (the state is re-read after the GitHub calls). That write bumps the revision, so a caller holding an older `expected_revision` gets one conflict, and because the engine's checkpoint has no state guard a task blocked in the very last instant can still receive it. No file of #12 is changed and no production switch exists: nothing calls the bridge automatically.

Identity rules of the bridge:

- The identity is mission, phase, task type (the engine task's `type`), target and schema version. The canonical key upper-cases the target, so ids that differ only in case ("bug-a" and "BUG-A") would share one issue. The default target is therefore the task id only when it is already upper case, matches the identifier alphabet and does not look like a hash target; every other id becomes `H-<32 hex of sha256(task_id)>`. Pass `target=` to override.
- Binding (`engine_bindings` table, created on open, older registry files gain it): before any GitHub call the registry pins the engine task id to its fingerprint (first binding wins, atomic). A later call that derives another identity (changed phase, type, target or schema version) raises `IdentityDrift` before any GitHub call, because it would create a second issue. This holds even when the first run crashed after the create, ended `BLOCKED`, or belonged to a `FIXED` task, none of which leave an engine checkpoint. Engine checkpoints play no part in this check, so a checkpoint from an older identity cannot lock a task. An operator moves a task on purpose with `registry.rebind_engine_task(task_id, fingerprint, key, note)` (incident `ENGINE_REBOUND`; the old issue stays untouched). Two engine tasks cannot share one identity (`EngineBindingConflict`, reported as `IdentityDrift`). The binding lives in the registry file: with a lost registry file it is lost too, and only the marker lookup of the same identity protects. Operating rule: back up the registry file, and never change the identity of a task after a registry loss. After `rebind_engine_task` an old opt-in engine checkpoint keeps its old issue number; the registry mapping (`issue_for_engine_task`) is the authority. A registry file written by an earlier intermediate state that holds two engine tasks on one identity is reported once on open (incident `ENGINE_BINDING_DUPLICATE`), and `issue_for_engine_task` raises `EngineBindingConflict` for both tasks until an operator rebinds all but one.

`GitHubRestGateway(repository, token)` (`github_gateway.py`) is the REST implementation of `IssueGateway`:

- `find_issues` lists `/issues?state=all` page by page and filters by marker (no search index). A short page ends the listing; more than `max_pages * 100` issues raise instead of guessing.
- `get_issue` returns `None` only for a confirmed 404 on a repository that is visible to the token (a 404 first triggers one `GET /repos/{repo}` every time, not cached; a private or misspelled repository raises). Rate limits, 403, 5xx and network errors raise `GitHubError`, so an outage never looks like "does not exist".
- Redirects are never followed and every 3xx is an error: a moved or transferred issue must not send a write to another issue. Every issue answer (GET and the PATCH answers of update and reopen) must carry the requested issue number and, when present, this repository's URL.
- `create_issue` sends the caller's `timeout` as a wall-clock limit for the whole request (a server that drips bytes cannot stretch it); only connection refused or a failed name lookup raise `CreateNotSent`. A timeout or any other failure is uncertain and the guard re-checks by marker. After a timeout the socket is shut down, the connection cannot reopen itself, and a request that was still connecting is dropped; bytes that were already on the wire may still reach GitHub, which is why a timeout is uncertain and the marker lookup decides. A worker stuck in name resolution lives until the resolver returns (daemon thread, it sends nothing). Connection refused on any other call is a `GitHubError`.
- `update_issue` rewrites only the section between `TIM_TASK_BODY_BEGIN`/`END` (or appends it), back-fills the marker, PATCHes only when the body changed and posts at most one audit comment per distinct reason. `mark_duplicate` posts one comment. `reopen_issue` reopens and comments. No method closes an issue.
- Known limits: `update_issue` reads the body and then patches it, so a human edit in between is overwritten (GitHub gives no conditional update here); an issue body that carries a second, foreign fingerprint marker is not cleaned. The token appears only in the `Authorization` header; errors carry the HTTP status and path, never the token or the response body (the fixed diagnostic texts of the built-in transport, such as `timed out after`, stay readable; any error of an injected transport is reduced to its type name). Plain http is refused except for a loopback test server. The account behind the token must be in `trusted_authors`, otherwise its own issues are ignored and a lost registry can lead to a second issue after an author rename or deletion.

The gateway is tested against an in-memory REST fake and a local HTTP server for the real transport (`tests/task_governance/`), and against github.com with the live check below (throw-away repository `tim-live-check`): the first live run (2026-10-01) found the lagging issue listing, which led to PR #137; a later run on `3ecf137` (2026-10-02) passed every check. The lookup changed after that run, so the current head must pass the live check again before #68 is closed. A live write to the production repository needs its own explicit yes.

### Pinned hint (registry v3)

The first claim of a task stores `authoritative_hint` and `legacy_issues` in the registry row, in the same transaction as the claim (`hint_issue`, `hint_legacy`). Every later run of a task that is not yet `MAPPED` uses the pinned hint even when the caller omits it, so a crash while adopting (e.g. `mark_duplicate` failing with a 502) or a block on another match cannot leave a later run without the information an earlier run had, and a hint-less restart can no longer create a second issue next to the legacy one. Rules:

- Same hint again: only adds `legacy_issues`.
- Different explicit hint: the task `BLOCKED`s as `HINT_CONFLICT` (candidates: pinned and requested hint). It stays blocked, also for hint-less runs, until an operator calls `registry.replace_hint(fingerprint, hint, legacy, note=...)`, which records `HINT_REPLACED` in `governance_incidents`.
- A hint rejected as `HINT_NOT_FOUND` or `HINT_INVALID` is replaced only when a different hint is given (`ensure_task` with another hint, or `unblock(..., hint=X)`). A plain `unblock` keeps the pinned hint, so an operator retry after a transient gateway error (a wrongly reported 404) cannot make the next run create a second issue; to drop a hint on purpose use `replace_hint(fp, None)`.
- After a claim is won, the pinned hint and legacy numbers come from the row the claim returned, not from what the caller read before (another run may have pinned them in between).
- `registry.replace_hint` works only on `BLOCKED` or `RELEASED` tasks; it is refused (returns `False`) while a worker holds the claim, because that worker's fencing token would not notice the change. `registry.unblock(fp, note, hint=..., legacy=...)` swaps a rejected hint for the replacement in the same transaction.
- A hint that differs from the issue a task is already mapped to is ignored and leaves a `HINT_IGNORED_MAPPED` incident.
- Registry files from releases 1 and 2 get the columns added on open, in one transaction (`user_version=3`, never downgraded). Open claims from such a file become `BLOCKED` as `MIGRATED_CLAIM` (their hint cannot be recovered); an operator checks GitHub and calls `registry.unblock(fp, note, hint=<authoritative issue>, legacy=[...])` when the task has a legacy issue without marker (the hint is pinned for every block reason; a different already pinned hint stays, use `replace_hint` to change it), or plain `unblock` when no legacy issue exists.
- One `TaskRegistry` object may be shared by threads (its methods are serialized by a lock); processes open their own object on the same file.
- The gateway account must be listed in `trusted_authors`, otherwise `_matches` cannot see the issues the gateway itself created and a failed create could be repeated.

## Create authority (#68 decision gate, path A)

A registry file is local to one host, so two hosts with two files could both pass every check of one registry and both create. The repository therefore names the one registry that may create, and `ensure_task` asks before every create (`src/task_governance/create_authority.py`).

- Every registry file has an id (`registry_meta`, created once, the same for all processes that open the file).
- The designation is an issue that an operator opens by hand with a trusted account. Its body carries exactly one marker `<!-- TIM_CREATE_AUTHORITY_V1 registry=<32 hex> repository=OWNER/NAME -->`. The gateway reads it by number (a single read is consistent, the listing lags) and allows a create only when the issue exists in this repository, is not a pull request, is open, was opened by one of the `trusted_authors` passed to `ensure_task` (`None` never qualifies), and names this registry and this repository (the pre-transfer name counts as the same repository).
- Anything else refuses: no authority configured, an unreadable or missing issue, a closed one, a second marker, another registry. A refusal is `BLOCKED` with detail `CREATE_NOT_AUTHORIZED`; it happens before the create intent is written, so it never leaves a `CREATE_UNCERTAIN` block behind, and the claim is released. A read error raises (nothing was created, the claim is released). Adoption, updates, reopen policy and duplicate handling work for every registry.
- A gateway built without a create authority never creates (`GitHubRestGateway(..., create_authority=None)` is the default), and a gateway object without `authorize_create` is refused by `ensure_task`. `live_check --mode roundtrip` uses `UnrestrictedCreateAuthority` on its throw-away repository; that class refuses the production repository, so `--allow-production-repo` no longer lets a round trip create there.

Setup on the one host that creates tasks (no GitHub write happens in code; the operator opens the issue):

1. `python -m src.task_governance.create_authority id --registry <registry file>` prints the registry id.
2. `python -m src.task_governance.create_authority body --registry <registry file> --repo OWNER/NAME` prints the issue body. Open an issue with that body (label it `governance`) with a trusted account and note its number `N`.
3. `TIM_LIVE_CHECK_TOKEN=<read-only token> python -m src.task_governance.create_authority verify --registry <registry file> --repo OWNER/NAME --issue N --trusted-author <login>` must print `"ok": true` (GET only).
4. Build the gateway with `GitHubRestGateway(repo, token, create_authority=IssueCreateAuthority(N))` and pass the same logins as `trusted_authors` to `ensure_task` / `sync_engine_task_to_issue`.

Operations: to revoke creation close the issue. To move the creator to another host (the handover) take three steps, never one: (1) close the old designation issue; (2) wait at least 4 minutes (an old host that is not paused sends its request within the create bound of 20 s after its last read of the designation, and a paused one is refused once it is 80 s late; the wait covers 80 s + 20 s twice plus a margin, and the create claim below covers whatever stands still longer); (3) open a new designation issue with the new registry's id and point the new host's gateway at it. Do not edit the marker of a designation issue by hand. The old host then adopts and updates but no longer creates. Even an old host that stands still longer than the wait (a paused process, a frozen VM) cannot make a second issue, because every create happens under the create claim below: it either creates the one issue, which the new host then adopts, or it is refused by its second check. A registry file that is copied to another host shares the original's id: run `registry.rotate_registry_id(note)` on the copy first (mappings stay, the new id is not designated). The same holds for a registry file restored from a backup while the original may still run, on the same host or another: rotate the restored file unless the original is known to be gone (two files of one lineage can both see the same run as ended and race for the label it left behind).

What this does and does not enforce. It enforces the code path: no component that goes through `ensure_task` creates a Mission-Task issue unless its registry is the designated one, across hosts and across separate registry files (`tests/task_governance/test_create_authority.py`: a race of two and of eight separate registries creates exactly one issue). It does not stop a person or tool with `Issues: write` from opening an issue directly, because GitHub cannot separate commenting from creating. Remaining windows: a person who may edit issues can edit the designation (the author check covers who opened it, not who last edited it); a copied registry file that was not rotated (it may replace a create claim its original still holds, see below); a person or tool that deletes a `tim-claim-…` label while the run that holds it is still alive. An issue created outside this path carries no marker; the post-create and the lost-registry checks still report a marker duplicate, nothing else would.

### Create claim and handover (#68, the handover race)

The designation check alone leaves a window: a creator reads the designation, stands still (a paused process, a slow network), the operator moves the designation to another registry, the other registry creates, and the first one goes on and creates too (found in the review of 2026-10-13: two issues with the one-step handover, also with a real `SIGSTOP`). Three things close it, in `ensure_task` after the create intent is recorded:

1. **The create claim.** Before the request the creator takes a repository-wide claim of the task: `claim_create` creates the label `tim-claim-<first 32 hex of the fingerprint>` (42 characters; GitHub allows 50) whose description says who holds it (`registry=<first 16 hex of the registry id> token=<claim token> host=<host> run=<run id> at=<UTC minute>`, no secret; the run id is 48 random bits drawn for every create attempt and stored in the claim row as `create_run`). GitHub creates a label at most once per name and answers 422 for a second create (the gateway then reads the label to confirm that it exists, so an invalid request is an error, never "held"), so two creators that both passed every local check cannot both hold the claim. A creator that does not get it returns `PENDING` / `GLOBAL_CLAIM_HELD` (one `GLOBAL_CLAIM_HELD` incident naming the holder; its claim is released, no create intent is left behind) and asks again on its next run; a creator whose label request got no answer reads the label once and goes on if it names its own run. Under the claim the creator looks the marker up a second time (an issue created under an earlier claim is visible now, and is adopted), asks the designation again (2.), reads the label once more right before the request (a label that does not name this run any more means no request: `PENDING` / `CLAIM_LOST_BEFORE_CREATE`, the run is noted as ended, nothing of its own is dropped), creates, checks for duplicates, records the result, and only then drops the label (`release_create_claim`; a failed drop is a `CLAIM_RELEASE_FAILED` incident, the issue is mapped all the same, and other registries find it by marker before they would ever claim). A label is deleted by name, so every drop reads it first and leaves it alone when it names another run by now (`CLAIM_NOT_OURS` incident). The label stays as long as the local row keeps its create intent: while the outcome of a request is uncertain (a timeout after the request, a lookup that failed after it) nobody creates behind it, neither this registry (`CREATE_UNCERTAIN`) nor another (`GLOBAL_CLAIM_HELD`); once the issue is visible and adopted, the label goes with it. On every path that gives up before the request the creator drops its label first, then notes in the registry that its run ended without a request (`claim_ends`), then releases the row. The note is what allows a later run of the same registry to replace a label that still names that run (`STALE_CLAIM_REPLACED` incident: the drop failed or its answer was lost; the replacement reads the label again and deletes it only while it still names the dead run, so two files of one lineage that replace at once leave one of them `GLOBAL_CLAIM_HELD`) and to clear a create intent that run left behind (`STALE_INTENT_CLEARED`: the crash came after the note). The note comes after the drop, so no run of this registry replaces the label while its holder could still delete it by name, and the operator's `confirm_not_created` adds the same note for the run whose intent it clears. Nothing else makes a label replaceable: not a lower token (a registry file restored from a backup reaches every token by retrying, but never has the run id of the original's live holder in its `claim_ends`), not the same registry or host alone (a copied file shares both; `host=` is a prefix of the host name plus a hash of the whole name, so a twin host does not count as this host either), not a text without a run id. A label whose holder died with its create intent recorded is handled with that row: the operator checks GitHub, knows the worker stopped, calls `confirm_not_created`, and the next run of the same registry replaces the label itself; a label of a host or registry that no longer exists, or one without a `run=` field (written by a version before the run id existed), is deleted by hand, and only by someone who knows its holder stopped. The incident reporter counts the claim and its release as writes (`CREATE_WRITES`, `writes_per_run` in `config/tim_checkup.json`). A gateway without `claim_create` never creates, like one without `authorize_create`.
2. **The second check and the freshness bound.** Right before the request the designation is read again, and that answer must be younger than `CREATE_FRESHNESS_SECONDS` (80 s, four times the default create bound of 20 s) when the creator decides to send, measured by whichever clock moved further (monotonic or wall: a paused process cannot hide time on both). The lookup under the claim is not part of that age: nobody else creates while the claim is held, so a long lookup (many direct reads in a fresh process) cannot make it stale. A creator whose designation was withdrawn in between, or that stood still longer than the bound between asking and deciding, is refused like any other `CREATE_NOT_AUTHORIZED` (claim and label released, no create intent left behind). What this does not cover, by construction, is a process that stands still between that decision and the request; that creator creates once under a designation that no longer holds, and the claim makes sure it is the only issue, which the new creator adopts.
3. **The three-step handover** above (close, wait, re-designate). With it the old creator is refused by its second check or has finished before the new designation exists; the claim is the safety net for every operator who skips the wait.

`tests/task_governance/test_handover_68.py` plays every pause (after the first check, under the claim before the second check, right before the request, a real `SIGSTOP` of a separate process), the freshness bound on both clocks, a held claim, a stale claim of a run that ended and of runs this registry never saw end (another host, a restored backup, a twin host, a lost label answer), a claim kept while the outcome is uncertain, a failed release, a label another run holds by now, a run of the same file that gives up while a sibling waits, and the same registry's paused run that is never taken over after its lease.

## Live check of the gateway (first run against github.com)

`python -m src.task_governance.live_check --repo OWNER/NAME` (module `src/task_governance/live_check.py`, tested against the in-memory REST fake). It is the evidence step that #68 still needs: the gateway has only been tested against a fake and a local HTTP server.

Token: read from the environment variable `TIM_LIVE_CHECK_TOKEN` only, never from arguments, never printed. Use a fine-grained token limited to the one repository (Issues: read for the read-only mode, Issues: read and write for the round trip). Revoke it after the run.

1. `--mode readonly` (default; only GET requests): repository visible, token user (`GET /user`), whole issue listing read, a missing issue number is a confirmed 404. `--probe-issue N` also reads one existing issue. Safe against the production repository with a read-only token.
2. `--mode roundtrip --confirm-write OWNER/NAME` (writes one issue): create, second run updates the same issue, a run with a fresh registry adopts it instead of creating another, and exactly one issue carries the marker. The gateway cannot close issues, so the test issue stays open and is closed by hand. Run it against a throw-away repository first. The production repository is refused unless `--allow-production-repo` is passed as well, and even then the round trip creates nothing there: its create authority refuses the production repository (see "Create authority").

First live finding (2026-10-01, throw-away repository): the REST issue listing does not show an issue created a moment earlier (it appeared about a minute later), while a read by number is consistent at once. A run with a lost registry therefore created a second issue and the final marker check saw nothing. `GitHubRestGateway.find_issues` now also reads, number by number, every number the listing leaves out below its highest entry and everything above it until three numbers in a row do not exist. It never stops below the highest number the gateway has created or seen, so the post-create check always reaches the issue it just made; a second creator that was blind before its own create therefore ends in `DUPLICATE_AFTER_CREATE` (loud), not in a silent duplicate. Old numbers (at least 50 below the highest entry) that answer 404, 410 or a redirect are remembered as missing only when a second such answer comes at least 120 seconds after the first and no good answer came in between (a remembered number is asked again after an hour and again needs two answers), so no single wrong answer hides an issue for good (404 matters because discussions share the number space). Numbers up to the highest known one are read without the per-lookup limit (the post-create check must reach its own issue) but at most 2000 per lookup; numbers this gateway created for another task are not read again. A create answer more than 2000 above the highest known number is used for the mapping but never raises that floor. All other reads are limited to 500 per lookup, and a lookup that reaches the limit raises before anything is created. If the duplicate check after a create fails (rate limit, outage), the task is BLOCKED as `POST_CREATE_CHECK_FAILED` with the new issue as its only candidate and an incident is recorded. Every later run re-checks without changing the row first: it reads the created issue by number (consistent while the listing lags) and looks up the marker again. If the re-check fails again, the row stays exactly as it was. If the issue is gone, a pull request, by an untrusted author or no longer carries the marker, the task blocks as `EXPECTED_ISSUE_INVALID`. If another marker issue exists, it blocks as `DUPLICATE_AFTER_CREATE` with all numbers (nothing is chosen, closed or commented). Only when the created issue is the sole marker issue is it adopted. None of these paths creates an issue; a gateway without `carries_marker` fails closed (`EXPECTED_ISSUE_INVALID`), and `registry.unblock` refuses `POST_CREATE_CHECK_FAILED` and `EXPECTED_ISSUE_INVALID` without `hint=<issue number>`, so a plain release cannot lead to a second create. While `find_issues` reads numbers directly, an answer 2xx other than 200 is an error. One gateway object may be shared by threads (its state is under a lock) but belongs to one repository. Cost: one request per number the listing leaves out on every lookup until it is remembered; with more than 500 permanently missing numbers the repository needs an operator. Known limit: numbers this gateway created for another task are not read again while the listing lags, so an issue whose body also carries another task's marker is seen only after the listing catches up. Not detected: a proxy that replays an old create answer, or a create answer that lacks the marker (checking it would turn a real create into a retry loop). A number the listing shows or any read by number answers clears any pending "missing" answer for it, and a read by number raises the floor of later lookups (bounded per lookup by the owed limit, which raises instead of guessing; if such an issue is deleted before the listing ever shows it, that gateway object keeps walking to it on every lookup and, more than 2000 numbers above the listing, raises until it is replaced: fail closed, never a create) (so the re-check of a created issue in a new process searches at least up to it). The re-check releases the block only if the row is still exactly the block it checked; a newer verdict of another worker stands. Within one shared registry the create intent (step 5) prevents a second create after a crash or lease takeover. Residual limit: with a lost or unshared registry, a first lookup that is blind to a hidden issue behind three or more missing numbers above the listing's highest entry creates a second issue, which the post-create check then reports (`DUPLICATE_AFTER_CREATE`); detection is not prevention, so run task creation from one place with one registry file. The live check (`lost_registry_adopts_instead_of_creating`, run with a new registry and a gateway without memory, like a new process) is the guard against github.com and must be rerun after changes to the lookup.

macOS with a python.org Python: if the run fails with `SSLCertVerificationError`, the interpreter has no CA file. Run the "Install Certificates.command" that ships with that Python, or set `SSL_CERT_FILE=/etc/ssl/cert.pem` for the one process. Certificate verification stays on; never switch it off.

Exit code 0 means every check passed, 1 a failed check (the output lists each check), 2 a refused call. Do not interpret a single green run as proof of the secondary-rate-limit and abuse-protection behaviour of GitHub; the run proves the contract on the real API for one task.
